## Runtime decision RUNTIME-001

**Decision: nominate the pinned Windows stack for a controlled reproduction probe, not for baseline acceptance.** It is the closest recorded end-to-end implementation on the local operating system. Reuse its invocation/import/conversion ideas while keeping v2 contracts independent of this backend. The documented Linux recipe at `33129...` remains a comparison/restoration candidate; its mutable base tag and unresolved dependency pins are insufficient for a reproducible deployment.

The Windows profile reports CPython 3.12, `torch==2.14.1`, `torchvision==0.29.1`, CUDA 13.0 framework wheels, local CPython 3.12 Windows wheels for PyTorch3D/nvdiffrast/SAM2, editable upstream sources and extra CUDA 12.6 sparse-kernel dependencies. These values come from the pinned branch manifest; this host has not been provisioned or certified against them. A lockfile referencing absent local wheels/editable directories is not a portable runtime. Neither the code branch nor the package receipt transfers the ignored model/source/binary files.

Before P2.1 acceptance, M1 must produce a runnable environment manifest with the effective source tree hash, every patch and native wheel hash, model/rig hash, Python/framework/driver/GPU identity, configuration, installation checks and logs. M2/M3 must verify native geometry conversion and preparation/native scale consistency; M4 must classify the penetration fallback and numerical changes. If Windows cannot pass required geometry/kernel checks, select the Linux candidate in a new recorded decision and repeat compatibility checks. Do not silently mix either upstream revision with another kit or rig.

A reproduction probe uses permitted episode-local inputs, a verified metric-mesh preparation, optional repair disabled, no quality bypass promotion, and a new immutable output. It preserves all native outputs even on failure. It must not load historical unknown-provenance demo/training assets or the archived legacy runtime directory. The initial deliverable is execution/conversion evidence for episodes 12 and 16; quality and export acceptance remain separate.

## Exposure decision and validation boundary

All 30 episodes' metadata has informed architecture. Episodes 0/1/2 have documented preparation exposure; 12/16 have documented repeated fitting, manual observations, visual review and candidate selection. The entire pan and grass-block object groups therefore belong to development for object-generalization claims, even where sibling-clip execution is unknown. Established dev-mini and newly proposed coverage roles also remain planning exposure, not evidence of actual inference. The ledger records the separate Physics pilot on episode 16.

All ten groups retain `clean_holdout_status: not_established`. External/manual history is unknown, and no untouched group is asserted. The initial policy uses retrospective grouped reporting and a future frozen-policy evaluation phase; any results subsequently used for policy changes become development evidence. Episode IDs cannot select solver thresholds or repairs. Same-object grouping controls evaluation leakage, not permission to pool reconstruction inputs.

P0.1 now has a source inventory and provisional runtime decision; local restoration and numerical verification remain open. P0.2 has a repository-evidence ledger, while external/manual exposure confirmation and actual video review remain open. P0.3 has a versioned structural/review protocol; runtime-specific conversion tolerances and numerical quality thresholds require baseline characterization before candidate ranking. None of G0-G4 closes through this audit.
